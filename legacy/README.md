# legacy — переезд с прежней системы

Требования: `REQ-MIG-REPORT`, `REQ-MIG-APPLY`, `REQ-MIG-CLIPS`, `REQ-MIG-LEGACY`
([`docs/SPEC.md §11`](../docs/SPEC.md)). Сценарий: `S-11`.

Модуль разовый. После успешной миграции он не участвует в работе приложения:
сервер, мост и интерфейс о нём не знают.

## 1. Что было не так с прежним пайплайном

Пять Python-скриптов, запускаемых по очереди через `RUN_ALL.bat`:

| Скрипт | Что делал | Чем это кончалось |
|---|---|---|
| `start1_tree.py` | создавал дерево папок `prompts/` | — |
| `start2_files.py` | писал `.md` с frontmatter | поле называлось `label`, не `title` |
| `start3_espanso.py` | генерировал конфиг espanso | третья копия текстов |
| `start4_link.py` | копировал библиотеку в `%USERPROFILE%\prompts` | вторая копия |
| `start5_hotkeys.py` | генерировал скрипт хоткеев | — |
| `fill.py` | держал тексты 25 промптов внутри себя, 425 строк | **перезапись правок** |

Три следствия, каждое проверено на настоящих данных:

1. **Три копии, ни одна не главная.** Правка в одном месте не доходила до
   остальных. Отчёт миграции показывает 27 промптов из 30 в двух копиях, и у 12 из
   них **тела разные**: в проекте лежит `TODO: вставить текст промпта`, а
   настоящий текст — в домашней копии. То есть рабочая версия была именно в той
   копии, которую пайплайн считал производной.
2. **`fill.py` мог затереть правку.** Тексты промптов были аргументами скрипта, а
   не данными: повторный запуск переписывал файл содержимым из кода. Именно
   поэтому файл выведен из пайплайна, а не «оставлен на случай».
3. **`score: -` в 22 файлах.** Прочерк означал «не оценивал», но `Number('-')`
   даёт `NaN`, и сводка показывала «NaN» на весь экран. Это тот самый симптом,
   с которого началась переделка.

Скрипты остались в корне проекта нетронутыми. Они больше ниоткуда не вызываются:
`RUN_ALL.bat` и `SYNC_MENU.bat` не входят ни в один путь нового приложения.

## 2. Порядок переезда

```
npm run migrate:report    # только читает и печатает, ничего не меняет
npm run migrate:apply     # копия источников → запись → сверка
```

Флаг обязателен. Команда без флага отказывается работать и объясняет, какие есть:
миграция сводит три копии в одну, и запуск «по привычке» тут недопустим.

### Что делает `--report`

Читает все найденные источники и печатает по каждому промпту:

- какая копия выиграла и **почему** одной фразой («version 1 против 0», «файл
  изменён позже», «источник важнее»);
- что потеряется, если тела копий разошлись;
- какие поля будут переименованы;
- где стоит прочерк вместо значения;
- конфликты `id`.

### Что делает `--apply`

Порядок операций не подлежит перестановке:

1. **резервная копия всех источников целиком**, включая проигравшие;
2. запись слитой библиотеки;
3. **сверка чтением с диска** — не доверяя отчёту той функции, которая писала.

Ни одного удаления. Исходные папки остаются на месте: миграция создаёт новую
библиотеку, а не переносит старую. Удалить источники — отдельное решение человека.

## 3. Как выбирается главная копия

Порядок сравнения фиксирован и проверяется именно в нём:

| # | Признак | Почему в этом месте |
|---|---|---|
| 1 | `version` | единственное поле, прямо заявляющее старшинство |
| 2 | `updated` | дату правки ставит автор |
| 3 | `mtime` | время файла; ненадёжно — копирование его переписывает |
| 4 | порядок источников | проект важнее домашней копии |

`mtime` **не первый** сознательно: `start4_link.py` копировал файлы, и у копии
время оказывалось новее оригинала. Доверие к нему потеряло бы настоящую правку.

## 4. Что меняется в файлах

| Было | Стало | Почему |
|---|---|---|
| `label:` | `title:` | одно имя поля на проект; два имени означают, что кто-то проверит только одно |
| `score: -` | `score: null` | прочерк — не число; `Number('-')` даёт `NaN` |
| `id` дублируется в двух группах | `s-hagent` + `s-hagent-inbox` | переименование, а не удаление: тела могут отличаться |
| HTML в теле | чистый текст | `cleanBody`, та же функция, что при сохранении из журнала |

`used` и `last_used` переносятся **как есть**: их пишет программа
([`docs/DATA-CONTRACTS.md §1.5`](../docs/DATA-CONTRACTS.md)), и обнуление
статистики потеряло бы историю, по которой строится порядок списка.

`AGENTS.md` в `templates/` остаётся как есть и назван в отчёте: `id` из заглавных
букв не проходит контракт, и переименовать его должен человек — это не промпт, а
шаблон.

## 5. Клипы ClipClip

```
node -e "import('./legacy/index.mjs').then(m => console.log(m.printableClips(m.planClips('ПУТЬ'))))"
```

Не переносятся, и каждый отказ назван:

- **картинки** — журнал хранит текст, вставлять картинку в чат нечем;
- **клипы из чёрного списка процессов** — запись из менеджера паролей не должна
  ожить в новом журнале;
- **пустые после очистки** — 19 из 39 клипов были HTML от Google Docs, и часть из
  них после снятия тегов не содержит ничего.

Имя записи берётся `titleFromText` — той же функцией, что при сохранении промпта
из журнала. Прежняя система резала первые 50 символов, и в списке стояли строки
вида «Проведи ревью кода ниже. Разбери по уровн…», по которым ничего не найти.

## 6. Границы модуля

`legacy` зависит от `contracts`, `library` и `clipboard`
([`arch.yaml`](../arch.yaml)). Разрешение узкое и осмысленное: миграция обязана
читать frontmatter тем же парсером и очищать тело той же функцией, иначе появится
второе мнение о формате файла промпта. Писать в `prompts/` она тоже обязана через
`library` — владелец сущности «Промпт» один.

Изначально модуль был описан как архив с `may_depend_on: []`. Когда в нём появился
код, гейт границ немедленно назвал четыре нарушения — и был прав: файлы
изменились, карта нет. Карта исправлена, а не обойдена.
